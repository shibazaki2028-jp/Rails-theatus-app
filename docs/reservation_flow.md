# 予約処理の設計メモ

## 予約作成の流れ

1. ユーザーが映画詳細または映画館詳細から上映スケジュールを選択する
2. 対象スケジュールに紐づくスクリーンの座席のみを表示する
3. ユーザーが座席と料金種別を選択する
4. サーバー側で以下を検証する
   - 座席が1つ以上選択されていること
   - 同じ座席が重複して選択されていないこと
   - 選択された座席が対象スクリーンに属していること
   - 各座席に料金種別が指定されていること
   - 指定された料金種別が存在すること
5. Reservation と ReservationDetail をトランザクション内で作成する

## 予約変更の流れ

予約変更では、予約人数とチケット種別の構成は変更せず、座席位置のみ変更できる仕様としています。

更新時には既存の ReservationDetail を削除し、新しい座席情報で ReservationDetail を作成し直します。
この処理をトランザクションで囲むことで、途中で保存に失敗した場合でも、変更前の予約詳細が失われないようにしています。

## 現在の制約

- 同一上映回・同一座席の重複予約は、ReservationDetail のバリデーションで防いでいます。
- ただし、同時リクエスト時の競合をDB制約で完全に防ぐ設計にはまだしていません。
- reservation_details が schedule_id を直接持たないため、DBレベルのユニーク制約を設計するにはテーブル設計の見直しが必要です。

## レビューで確認したい点

- 予約更新処理におけるトランザクションの使い方は妥当か
- Reservation と ReservationDetail の責務分割は適切か
- 同時予約を防ぐためには、どのようなDB制約・テーブル設計にするのがよいか
