# 予約処理の設計メモ

## 予約作成の流れ

1. ユーザーが映画詳細または映画館詳細から上映スケジュールを選択する
2. 対象スケジュールに紐づくスクリーンの座席のみを表示する
3. ユーザーが座席と料金種別を選択する
4. サーバー側で以下を検証する
   - 座席が1つ以上選択されていること
   - 同じ座席が重複して選択されていないこと
   - 選択された座席が対象スクリーンに属していること
   - 各座席に料金種別が指定されていること
   - 指定された料金種別が存在すること
5. Reservation と ReservationDetail をトランザクション内で作成する
   - ReservationDetail の `schedule_id` は、保存前に親の Reservation からコピーする
   - 同じ上映回・同じ座席がすでに予約されていれば、バリデーションで弾く
   - 同時予約でバリデーションをすり抜けた場合は、DBの一意制約で保存が失敗し、トランザクション全体がロールバックされる。この場合は「ほかの利用者に予約された」ことを伝えて予約画面に戻す

## 予約変更の流れ

予約変更では、予約人数とチケット種別の構成は変更せず、座席位置のみ変更できる仕様としています。

更新時には既存の ReservationDetail を削除し、新しい座席情報で ReservationDetail を作成し直します。
この処理をトランザクションで囲むことで、途中で保存に失敗した場合でも、変更前の予約詳細が失われないようにしています。

対象の上映回は、リクエストのパラメータではなく、変更対象の Reservation 自身から取得します。

削除してから作成し直す順序のため、自分の予約の座席を入れ替える場合でも、同じ上映回・同じ座席の行が一時的に2件存在することはなく、一意制約とは衝突しません。

## 同時予約への対策

同一上映回・同一座席の重複予約は、次の2段階で防いでいます。

| 層 | 仕組み | 役割 |
|---|---|---|
| アプリケーション | ReservationDetail のバリデーション（`seat_availability_check`） | 保存前に重複を見つけ、利用者に分かりやすく伝える |
| DB | `reservation_details` の `(schedule_id, seat_id)` 一意制約 | 同時にリクエストが届いても、重複したデータを保存しない |

### テーブル設計

`reservation_details` に `schedule_id` を持たせ、`(schedule_id, seat_id)` に一意制約を設定しています。

- `schedule_id` は NOT NULL。NULL を許すと、一意制約をすり抜ける行が作れてしまうため
- `schedules` への外部キーを設定
- `schedule_id` は親の Reservation からのコピーで、保存前に常に上書きする（`before_validation`）

複合インデックスは `schedule_id` を先頭にしているため、「ある上映回の予約済み座席」を探す検索にも使えます。そのため、`schedule_id` 単独のインデックスは作成していません。

### 既存データの移行

マイグレーションでは、次の順序で処理しています。

1. NULL を許可した状態で `schedule_id` を追加する
2. 既存の予約詳細に、親の予約の `schedule_id` を書き写す
3. 同じ上映回・同じ座席の重複がないことを確認する（あればマイグレーションを中止する）
4. NOT NULL にする
5. 一意制約を設定する

### 現在の制約

- 予約詳細と親の予約の上映回が一致していることは、アプリケーション側（`before_validation`）で保証しています。SQLを直接実行した場合までは、DBレベルで保証していません。DBで保証するには、`(reservation_id, schedule_id)` で予約を参照する複合外部キーが必要です
- 予約のキャンセルは予約詳細の削除で表現しているため、一意制約と矛盾しません。キャンセル履歴を残す形に変える場合は、一意制約の対象を見直す必要があります
