# Theatus - 映画館予約システム

大学の授業内で制作した、映画館の座席予約システムです。

要件定義、ユースケース図、ER図の作成から実装までを行いました。
チームで要件定義・ER図を共同設計し、同一仕様をもとに個人で実装しています。

授業内では映画館予約システムとしての基本機能を実装し、現在は予約変更時のデータ整合性、認可、テストを中心に、より堅牢な設計へ改善を進めています。

## アプリの概要

ユーザーが映画・映画館・上映スケジュールを確認し、希望する座席を選択して予約できるWebアプリケーションです。

主な利用フローは以下です。

1. 映画または映画館を検索・閲覧する
2. 映画詳細または映画館詳細から上映スケジュールを選ぶ
3. 座席と料金種別を選択する
4. 予約内容を確認して確定する
5. マイページから予約確認・変更・取消を行う

## 権限設計

アカウントには以下のロールがあります。

| ロール | 概要 |
|---|---|
| general | 一般ユーザー。自分の予約のみ作成・閲覧・変更・取消できる |
| theater_admin | 映画館管理者。管理者向け機能の一部を利用する想定 |
| system_admin | システム管理者。管理者向け機能を利用できる |

一般ユーザー向けのアカウント更新では、role を受け取らないようにし、リクエスト改ざんによる権限昇格を防いでいます。

## 工夫した点

### 予約変更時のデータ整合性

予約変更では、既存の予約詳細を削除してから新しい座席情報を保存する必要があります。

当初は、既存の予約詳細を削除した後に新しい予約詳細を保存する処理として実装していました。しかし、保存途中で失敗した場合、古い座席情報だけが消え、予約内容が壊れる可能性があることに気づきました。

授業ではトランザクション処理を詳しく扱っていなかったため、まずは更新前の予約詳細を退避し、失敗時に復元する処理を実装しました。その過程で、複数のDB更新を一つの処理単位として扱う必要性を理解しました。

現在はその学びを踏まえ、ActiveRecord の transaction を用いて、予約更新処理の原子性を担保する実装へ改善しています。

### 認可処理の改善

予約詳細・編集・取消では、一般ユーザーが他人の予約をURLから直接操作できないように、予約取得時点で current_account に紐づく予約だけを取得するようにしています。

また、未ログイン状態で予約関連画面にアクセスした場合は、ログイン画面へリダイレクトするようにしています。

### 不正なパラメータへの対策

座席選択では、画面上の制御だけでなく、サーバー側でも以下を検証しています。

- 選択された座席が対象スクリーンに属していること
- 同じ座席が重複して選択されていないこと
- 料金種別が存在すること
- 各座席に料金種別が指定されていること

## テスト

以下の観点をMinitestで確認しています。

- 未ログインでは予約一覧にアクセスできない
- 他人の予約詳細にはアクセスできない
- 別スクリーンの座席IDでは予約を作成できない
- 予約更新に失敗しても変更前の座席情報が残る

実行方法:

```bash
bin/rails test
```
