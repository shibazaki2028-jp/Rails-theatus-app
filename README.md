# Theatus - 映画館予約システム

大学の授業内で制作した、映画館の座席予約システムです。

要件定義、ユースケース図、ER図の作成から実装までを行いました。
チームで要件定義・ER図を共同設計し、同一仕様をもとに個人で実装しています。

授業内では映画館予約システムとしての基本機能を実装しました。授業後も改善を続けており、外部のエンジニアから受けたコードレビューをもとに、予約変更時のデータ整合性、認可、同時予約への対策（DB制約）、テストを強化しています。

## アプリの概要

ユーザーが映画・映画館・上映スケジュールを確認し、希望する座席を選択して予約できるWebアプリケーションです。

主な利用フローは以下です。

1. 映画または映画館を検索・閲覧する
2. 映画詳細または映画館詳細から上映スケジュールを選ぶ
3. 座席と料金種別を選択する
4. 予約内容を確認して確定する
5. マイページから予約確認・変更・取消を行う

## 権限設計

アカウントには以下のロールがあります。

| ロール | 概要 |
|---|---|
| general | 一般ユーザー。自分の予約のみ作成・閲覧・変更・取消できる |
| theater_admin | 映画館管理者。管理者向け機能の一部を利用する想定 |
| system_admin | システム管理者。管理者向け機能を利用できる |

一般ユーザー向けのアカウント更新では、role を受け取らないようにし、リクエスト改ざんによる権限昇格を防いでいます。

## 工夫した点

### 予約変更時のデータ整合性

予約変更では、既存の予約詳細を削除してから新しい座席情報を保存する必要があります。

当初は、既存の予約詳細を削除した後に新しい予約詳細を保存する処理として実装していました。しかし、保存途中で失敗した場合、古い座席情報だけが消え、予約内容が壊れる可能性があることに気づきました。

授業ではトランザクション処理を詳しく扱っていなかったため、まずは更新前の予約詳細を退避し、失敗時に復元する処理を実装しました。その過程で、複数のDB更新を一つの処理単位として扱う必要性を理解しました。

その学びを踏まえ、現在は ActiveRecord の transaction を用いて、予約更新処理の原子性を担保しています。更新に失敗しても変更前の座席が残ることは、テストで確認しています。

### 同時予約への対策（DB制約）

座席の重複予約は、保存前のバリデーションで確認していました。しかし、2人がほぼ同時に同じ座席を予約すると、どちらも「まだ予約されていない」という確認を通過し、二重予約になる可能性があります。そこで、DBでも重複を防ぐようにしました。

もともとのテーブル構造では、上映回（`schedule_id`）は予約（`reservations`）に、座席（`seat_id`）は予約詳細（`reservation_details`）にあり、「同じ上映回・同じ座席は1件まで」という一意制約を直接設定できませんでした。

レビューで示された複数の設計案を比較し、「1つの予約は1つの上映回」という現在の形を保ちつつ、変更範囲を小さくできる案を選びました。

- `reservation_details` に `schedule_id` を追加し、`(schedule_id, seat_id)` に一意制約を設定
- `schedule_id` は保存前に常に親の予約からコピーし、予約と予約詳細で上映回がずれないようにする
- 既存データは、マイグレーションの中で親の予約から値を埋め直してから、NOT NULL と一意制約を設定
- 一意制約に違反した場合は、エラー画面ではなく「ほかの利用者に予約された」ことを伝えて予約画面に戻す

保存前のバリデーションは利用者に分かりやすく伝えるため、DBの一意制約は同時にリクエストが届いても不正なデータを保存しないため、と役割を分けて両方残しています。

なお、予約と予約詳細の上映回の一致はアプリケーション側で保証しており、DBレベルでは保証していません。また、上映回ごとの座席を表すテーブルを設ける案のほうが、仮押さえや販売停止などの状態管理には拡張しやすいと考えており、今後の検討事項としています。

### 認可処理の改善

予約詳細・編集・取消では、一般ユーザーが他人の予約をURLから直接操作できないように、予約取得時点で current_account に紐づく予約だけを取得するようにしています。

また、未ログイン状態で予約関連画面にアクセスした場合は、ログイン画面へリダイレクトするようにしています。

予約変更では、リクエストに含まれる上映回IDではなく、予約自身の上映回を使うようにしています。以前はリクエストに上映回IDを付け加えると、別のスクリーンの座席に変更できてしまう問題がありました。先にこの問題を再現するテストを書き、修正後にテストが通ることを確認しています。

### 不正なパラメータへの対策

座席選択では、画面上の制御だけでなく、サーバー側でも以下を検証しています。

- 選択された座席が対象スクリーンに属していること
- 同じ座席が重複して選択されていないこと
- 料金種別が存在すること
- 各座席に料金種別が指定されていること

## テスト

以下の観点をMinitestで確認しています。

### 統合テスト（`test/integration`）

- 未ログインでは予約一覧にアクセスできない
- 他人の予約詳細にはアクセスできない
- 別スクリーンの座席IDでは予約を作成できない
- 予約更新に失敗しても変更前の座席情報が残る
- リクエストに別の上映回IDを付けても、別スクリーンの座席に変更できない
- 同時予約でバリデーションをすり抜けても、DBの一意制約で止まり、予約作成画面に戻る
- 同時予約でバリデーションをすり抜けても、DBの一意制約で止まり、変更前の座席が残る

同時予約の状況は、テストの中だけ座席の重複チェックを一時的に止めることで再現しています。

### モデルのテスト（`test/models`）

- 別の上映回IDを渡しても、予約詳細の上映回は親の予約に揃う
- バリデーションを飛ばしても、DBの一意制約が同じ上映回・同じ座席の2件目を拒否する
- 同じ上映回・同じ座席の2件目は、バリデーションで無効になる
- 親の予約がない予約詳細は無効になる
- 保存済みの予約詳細をもう一度バリデーションしても、自分自身とは衝突しない

実行方法:

```bash
bin/rails test
```

## レビューを受けて対応したこと

外部のエンジニアにコードレビューを依頼し、以下の点について助言を受けました。

| 相談した点 | 対応 | 状態 |
|---|---|---|
| 予約作成・予約変更処理の責務分割 | 予約変更のトランザクション部分を専用クラスに分ける方針を検討中 | 未対応 |
| Reservation と ReservationDetail の設計 | 予約詳細に上映回を持たせ、一意制約を設定できる構造にした | 対応済み |
| 認可処理の置き場所 | 現在の規模では before_action で扱う形を維持。条件が増えた段階で専用クラスへの切り出しを検討する | 現状維持 |
| 同一上映回・同一座席への同時予約 | DBの一意制約を追加し、違反時の画面表示とテストを整備した | 対応済み |
| 優先して改善すべき点 | 同時予約対策とテストを優先して対応した。テストの自動実行（CI）は今後対応する | 一部対応 |

## 今後改善したい点
